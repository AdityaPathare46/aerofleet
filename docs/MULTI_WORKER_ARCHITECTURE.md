# Multi-Worker Architecture (Phase AH)

## The problem

AeroFleet's backend has always run `uvicorn ... --workers 1`. `FleetState`,
`DroneLinkRegistry`, and `AsyncEventBus` are module-level singletons
(`aerofleet/fleet/state.py`, `aerofleet/hardware/telemetry_service.py`,
`aerofleet/event_bus/async_bus.py`) — each worker process would get its own,
independent copy. Two concrete failures follow from that:

1. **Duplicate hardware connections.** `DroneLinkRegistry.register()` opens
   a real MAVLink connection (serial or UDP) to a physical drone. If two
   worker processes both called `register()` for the same `drone_id`, two
   processes would be writing setpoints to the same link, racing each
   other — a genuine safety problem, not just an inefficiency.
2. **Broken WebSocket fanout.** `aerofleet/api/routes/hardware.py`'s
   `/ws/telemetry` endpoint only broadcasts events published on *its own
   process's* `AsyncEventBus`. A client connected to worker B would never
   see telemetry generated by worker A's `DroneLinkRegistry.run_forever()`
   poll loop, because nothing bridged the two processes.

## The constraint that shapes the fix

No amount of shared state removes the fact that a MAVLink link is a
**single-owner resource**. Redis (or any other shared store) doesn't change
that — it only helps with problem #2, not problem #1. Trying to make every
worker fully symmetric ("just put FleetState in Redis and scale out") would
either re-introduce the duplicate-connection problem or require building
real distributed locking/consensus for every hardware command, which is a
much bigger project than what a college capstone needs and would be
overclaiming if presented as "solved" here.

The design AeroFleet actually ships is therefore: **exactly one worker owns
real hardware and FleetState mutation; every other worker serves read
traffic and WebSocket fanout, receiving events via Redis pub/sub instead of
its own MAVLink polling.**

## What's built

### 1. `AEROFLEET_HARDWARE_OWNER` — the ownership gate

`aerofleet/api/routes/hardware.py::hardware_owner_enabled()` reads this env
var. Unset (or `1`/`true`) means "this process owns hardware" — the exact
behavior every version of AeroFleet had before this phase, since a
single-process deployment has nothing to disambiguate. In a real
multi-worker deployment, set `AEROFLEET_HARDWARE_OWNER=0` on every worker
process except the one designated as the owner (e.g. via each worker's own
environment in your process manager / k8s pod spec — this repo doesn't ship
a specific orchestration config for it, since that depends on your actual
deployment target).

Effect: `hardware.start_background_polling()` — which starts
`DroneLinkRegistry.run_forever()`, the loop that actually opens/polls
MAVLink links — only runs on the owner. Non-owner workers still expose
`/api/v1/hardware/*` REST endpoints and the `/ws/telemetry` WebSocket
normally; they just don't run their own MAVLink poll loop.

### 2. `aerofleet/event_bus/redis_bus.py` — cross-worker event relay

`RedisEventBridge` wraps the existing `AsyncEventBus`-based telemetry path,
additively:

- `relay_to_redis(event)` — called from the same local subscriber
  (`_on_telemetry_event` in `hardware.py`) that already broadcasts an event
  to this process's own WebSocket clients. When `AEROFLEET_REDIS_URL` is
  set, it also publishes a JSON envelope (`{"origin": <per-process uuid>,
  "event": {...}}`) to the `aerofleet:events` Redis pub/sub channel. A
  relay failure is caught and logged, never raised — the local WS clients
  already got the event via the normal path before this is even called.
- `listen_forever()` — a background task (started alongside the other
  background workers in `app.py`'s startup event, on *every* process, owner
  or not) that subscribes to `aerofleet:events` and invokes
  `on_relayed_event(event)` for each message whose `origin` isn't this same
  process's own id. `hardware.py` wires that callback straight to
  `_broadcast()` — bypassing the normal `AsyncEventBus` subscriber list
  entirely, which matters: if a relayed event were re-published through the
  normal local bus, it would re-trigger `_on_telemetry_event` →
  `relay_to_redis()` again, sending it back out to every worker — an
  unbounded ping-pong loop. `_on_redis_relayed_event` exists specifically
  to avoid that.
- With `AEROFLEET_REDIS_URL` unset, `get_redis_client()` returns `None`,
  `redis_enabled` is `False`, `relay_to_redis()` is a no-op, and
  `listen_forever()` returns immediately — single-process deployments are
  byte-for-byte unchanged from before this phase.

### 3. Bug fixed along the way

`hardware.py`'s `start_background_polling()`/`stop_background_polling()`
had the same singleton-reset bug Phase AF found and fixed in
`explanation_worker.py`, `policy_review_worker.py`, and
`incident_forensics_worker.py` — `stop_background_polling()` called
`registry.stop()` but never reset the module-level `_polling_task` back to
`None`. A second `startup_event` within the same process (the exact
scenario a multi-`TestClient` pytest session creates) would then see
`_polling_task is not None` and silently never restart telemetry polling.
This phase's audit of the hardware-owner logic surfaced it; fixed the same
way as the other three.

### 4. Request-level enforcement on mutating endpoints (follow-up)

The first version of this phase left dispatch/hardware mutations to
deployment-level routing alone — no in-app check stopped a non-owner
worker from accepting `POST /orders/{id}/dispatch` or
`POST /hardware/vehicles/{id}/arm` and silently mutating its own
uninitialized `FleetState`/`registry` (or, worse, `emergency_stop_all`
looking like a 200-success while RTLing zero vehicles, because a non-owner
worker's `registry._links` is always empty).

`require_hardware_owner()` (`aerofleet/api/routes/hardware.py`) closes that
gap: a FastAPI dependency, applied to every mutating hardware endpoint
(`connect_vehicle`, `disconnect_vehicle`, `arm_vehicle`, `disarm_vehicle`,
`emergency_stop_all`) and called directly at the top of `orders.py`'s
`dispatch_order`, that raises `HTTPException(503, ...)` whenever
`hardware_owner_enabled()` is false. Deliberately **not** applied to
read-only endpoints (`GET /hardware/vehicles`) — those still return
whatever this worker's own state happens to be, which is the accepted,
documented read-mirror gap below, not something this check tries to fix.

The 503 is the right status here, not 403/409: it's not an auth failure or
a conflict with existing state, it's "this specific server instance can't
service this request type right now, ask a different one" — the same
semantic a load balancer already uses to mean "try another backend."

## What's deliberately NOT built (and why)

- **No cross-worker FleetState read-mirror.** A non-owner worker's
  `GET /api/v1/fleet/*` endpoints currently read that worker's own
  (empty/uninitialized) `FleetState`, not the owner's. Building this
  correctly — publishing snapshots to Redis, deciding a staleness bound,
  handling partial-update races — is a real distributed-systems project on
  its own. Presented honestly here as a gap, not glossed over: **in a real
  multi-worker deployment today, GET endpoints on non-owner workers will
  not reflect live fleet state.** The practical mitigation is to route all
  HTTP traffic (not just hardware control) to the owner worker via your
  reverse proxy / load balancer's session affinity, and use the extra
  workers only for the async LLM council/explanation/policy/incident-
  forensics background work, which already doesn't touch `FleetState`
  directly on the request path. (Mutations, unlike reads, now fail loudly
  instead of silently — see §4 above.)

## Verification

- `tests/unit/test_redis_event_bridge.py` (15 tests) — no-Redis-configured
  pass-through behavior, relay/publish call shape, relay-failure resilience,
  the self-vs-foreign origin discrimination that prevents the ping-pong
  loop, malformed-payload handling, and the `AEROFLEET_HARDWARE_OWNER` gate
  logic. All mock the redis client — no real server required to run the
  suite.
- **Live verification against a real `redis-server`** (not mocked): started
  a local Redis instance, then ran two genuinely separate OS processes —
  one publishing a `telemetry.update` event via `relay_to_redis()`, the
  other subscribed via `listen_forever()` — and confirmed the event
  actually crossed the process boundary through Redis pub/sub end to end.
  This is the scenario unit tests with a single process and a shared
  `_PROCESS_ID` cannot exercise (both bridges in one process would share
  the same origin id and the self-relay guard would suppress it — correct
  for the real deployment, but it means the cross-process path specifically
  needed a real multi-process check, not just mocks).
- `tests/integration/test_hardware_owner_gate.py` (11 tests, follow-up) —
  every mutating hardware endpoint and dispatch itself 503 when
  `AEROFLEET_HARDWARE_OWNER=0`; all work normally when unset or `"1"`;
  read-only `GET /hardware/vehicles` is confirmed NOT gated; a non-operator
  request against a non-owner worker is confirmed to never succeed (403 or
  503, never 200) so the new gate can't be used to bypass the existing
  operator check.
- `pytest tests/` full suite: no regressions, same pre-existing
  `test_config.py` failure as every prior phase.
